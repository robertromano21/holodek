# Game Process Lifecycle

Closing the last application window initiates automatic shutdown after the existing ten-second refresh/reconnect grace. No player command or PowerShell step is required. Reloading or keeping another game window open cancels the pending shutdown. A configured startup grace delays shutdown; it cannot suppress the only close event indefinitely.

Double-click `Start Holodek.vbs` to start and open the game without a terminal. The hidden launcher validates the PM2 application's exact project, script and port, applies the existing ecosystem configuration when starting a stopped/legacy idle server, waits for health plus native containment, then opens `http://localhost:3000/assets/index.html` in a new Chrome Incognito window. It finds Chrome in the usual system/per-user installation locations, or uses an explicit `CHROME` executable path. It never falls back to a non-private browser. The launcher exits after Chrome starts rather than waiting for the browser to close. An already-open adventure is reused, never restarted. An unresponsive or unknown process is left untouched and a startup error is recorded instead of killing it. `gameServer2` is never a launch target.

A stale PM2 entry can have PID zero while an older game still owns port 3000. The launcher does not mistake this for a dead server or kill the listening PID. With no game windows connected, it proves project ownership through a fresh random static-file round-trip, reads the current adventure's event stream, rechecks identity and windows, clears only `gameServer`'s stale restart scheduling, and requests the application's guarded Quit. Busy games, failed ownership proofs, changed identities and refused shutdowns stop recovery. It waits for the listener to close before starting the contained release. The transient proof file and event-stream connection are always cleaned up.

Shutdown stops accepting connections, pauses gameplay, cancels adjacent-room jobs and retries, aborts website/model requests, rejects pending local inference, and stops voice, audio-palette and semantic-memory workers. It waits for cancellation before flushing logs and exiting, with a five-second hard deadline. An explicit Quit and PM2 shutdown signals use the same path. Connection settings and saves are not erased.

On Windows, `server.js` establishes an unnamed, per-instance Job Object before loading any game subsystem. A hidden watchdog holds its only job handle and waits on the exact server process handle, not a later PID lookup. All subsequently spawned children inherit containment, including subprocesses started inside worker threads, synchronous audio tools and detached grandchildren. Closing the handle after a clean exit or crash terminates any remaining members. The watchdog then exits as well. Failure to establish containment stops startup before workers launch. There is no process-name-wide kill, WMI process scan, or recursive PID-tree guess.

The PM2 daemon, `gameServer2`, other application instances, pre-existing Ollama, and installed shared website helper listeners are outside this job. Only this instance's requests, streams and room workers are cancelled. Cloud jobs use capability-bound cancel RPCs; remote room streams emit lightweight heartbeats so an SSH channel closing aborts the corresponding room HTTP request and worker, without stopping other players' jobs. The saved helper configuration remains enabled for the next launch.

The existing ecosystem configuration must govern the PM2 application: `stop_exit_codes: [0, 73]` prevents a deliberate close or duplicate-port exit from restarting the server. Crash recovery remains separately bounded by PM2. This is deployment configuration, not a task players should perform each time they finish playing.

Tests include real Windows containment with a detached, reparented grandchild and an unrelated sentinel; normal last-window closure; forced owner exit; multiple windows; refresh; startup grace; asynchronous/hung cleanup; queued and active inference/room/audio cancellation; and stream-isolated cancellation. No active saved adventure is used by these tests.

Native behavior references: [Windows Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects), [AssignProcessToJobObject](https://learn.microsoft.com/en-us/windows/win32/api/jobapi2/nf-jobapi2-assignprocesstojobobject).
